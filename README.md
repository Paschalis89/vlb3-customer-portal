# VLB3 Customer Portal - STEP 9

Customer-facing portal for the VLB3 platform.

STEP 9 adds customer organization user management. Owners and Admins can list users, invite new people, change assignable roles and activate/deactivate access. The Owner role is protected and cannot be assigned or modified from the Customer Portal.

## Backend requirement for STEP 9

No backend is required while:

```env
VITE_DEMO_MODE=true
```

The Users API abstraction is:

```text
src/api/users.ts
```

In demo mode the source of truth is:

```text
src/demo/users.ts
```

Real mode is already isolated behind the following intended API contracts:

```text
GET   /api/customer/users
POST  /api/customer/users/invitations
PATCH /api/customer/users/:userId
PATCH /api/customer/users/:userId/status
```

The backend must still re-check authentication, organization ownership and permissions during STEP 12. Frontend route guards are not considered a security boundary.


## User management rules

The Customer Portal applies these MVP rules:

```text
Owner
  -> visible
  -> protected
  -> cannot be edited, disabled or reassigned

Current account
  -> visible
  -> cannot edit or disable itself from /users

Admin / Operator / Viewer
  -> can be edited by an authorized Owner/Admin
  -> can be activated or disabled

New invitation
  -> role can only be Admin, Operator or Viewer
  -> Owner is never available in the role selector
```

The same rules must later be enforced by NestJS.

## STEP 9 test

Login as Owner:

```text
owner@demo.vlb3.local
Demo123!
```

Open:

```text
http://localhost:8080/users
```

Expected initial state:

```text
4 active users
0 invited users
0 disabled users
```

Suggested checks:

1. Invite a new Viewer.
2. Verify that the new account appears as `Invitato`.
3. Try logging in with the invited account: access must be refused while it is pending.
4. Activate the invited account.
5. Login with its email and `Demo123!`: access must work as Viewer.
6. Login again as Owner and disable the new account.
7. Verify that the disabled account can no longer login.
8. Verify that the Owner row cannot be edited or disabled.
9. Login as Admin and verify `/users` is available.
10. Login as Operator or Viewer and verify `/users` is hidden and direct navigation is rejected.

## STEP 10 - PWA

Versione: `0.10.0`

Il Customer Portal è ora predisposto come Progressive Web App installabile.

### Funzionalità aggiunte

- manifest generato durante il build usando `VITE_APP_NAME`;
- icone 192x192, 512x512, maskable e Apple Touch Icon;
- service worker registrato solo nel build di produzione;
- modalità `standalone`;
- supporto "Aggiungi alla schermata Home";
- prompt di installazione sui browser Chromium compatibili;
- istruzioni dedicate per Safari su iPhone/iPad;
- banner globale quando il browser è offline;
- supporto safe-area per dispositivi con notch/home indicator;
- aggiornamento del service worker senza caching aggressivo dei dati dinamici.

### Strategia cache

Il service worker può memorizzare la shell dell'app e gli asset statici necessari per riaprire il portale.

Non mette in cache le richieste `/api`, quindi telemetria, allarmi, stato comandi e altri dati dinamici non vengono mai serviti dalla cache come se fossero realtime.

In assenza di connessione il portale mostra un avviso esplicito.

### Test PWA in Docker

```bash
docker compose down
docker compose build --no-cache
docker compose up -d
docker compose ps
```

Aprire quindi il portale su HTTPS quando viene pubblicato sul server. In locale `localhost` è considerato un contesto sicuro dai browser moderni per lo sviluppo PWA.

Per verificare il manifest:

```bash
curl -i http://localhost:8080/manifest.webmanifest
```

Per verificare il service worker:

```bash
curl -i http://localhost:8080/sw.js
```

Nel browser usare DevTools > Application per controllare Manifest e Service Workers.
